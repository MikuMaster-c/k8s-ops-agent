# k8s-ops-agent

一个跑在它自己要观测的集群上的 K8s 运维诊断 Agent。两层：

```
应用层  规则发现 → LLM 解释 → 结构化输出 → 评测回归
交付层  kind 部署 → 三层探针 → 容器日志排障
```

## 两个入口

| 接口 | 做什么 | 值得看的设计 |
|---|---|---|
| `POST /diagnose` | 给一个 Pod 名和问题，返回带引用的诊断 | 规则先摘异常，模型只解释证据 |
| `POST /manifest` | 给自然语言需求，返回 Deployment 并按规则校验 | 校验失败带着问题重新生成，限两轮 |

## 为什么规则在前

模型不知道 `ImagePullBackOff` 该看 Events 而不是容器日志。所以 `rules.py` 用一张
状态到字段路径的映射表先产出 evidence，模型只在这些 evidence 里做解释。
引用越界由 `schema.bad_citations()` 事后检查——这就是本项目的
"AI output validation"，一次集合比对，不是形容词。

## 部署

```bash
uv sync
ollama pull qwen2.5:7b-instruct && ollama pull nomic-embed-text
bash scripts/docs.sh          # 拉 k8s 中文文档 → 建索引
uvicorn agent.app:app --reload

python -m eval.run_eval       # 20 条评测
python -m eval.compare        # 7B vs 3B 对照实验，写 eval/compare.json
bash scripts/build.sh         # kind 部署
```

## 三个刻意的减法

1. **没有向量库服务。** 两百条文档用朴素余弦，`rag.py` 里 8 行。Milvus 解决的是十万级以上的问题。
2. **没有重试和兜底。** 调用失败就是失败，评测会告诉你失败率。
3. **没有抽象层。** `kubectl` 一个函数、模型一个出口、数据源就两个。加抽象等有第三个数据源再说。

## 为什么只有一档模型

最初的设计是三级漏斗：规则 → 3B → 7B，引用校验不通过就升级。级联**没有上线**，
依据是 `eval/compare.py` 在同一批 20 条用例上的实测：

| 模型 | 通过率 | P50 | P95 |
|---|---|---|---|
| qwen2.5:7b-instruct | 15/20 | 7.3s | 9.0s |
| qwen2.5:3b-instruct | 3/20 | 4.0s | 9.6s |

3B 快约 1.8 倍，但通过率只有 3/20。按这个结果，"小模型直接放行"等于放行错误答案；
而"每个问题都先跑一遍 3B 再升级"会把 P50 抬到 11.3s，结果还更差。所以在 8GB 单卡上，
级联的收益是负的。这个结论本身就是要写进 README 的东西。

显存是硬约束：7B Q4 占 4.7 GB、3B 占 1.9 GB，桌面还要 3–4 GB，8 GB 装不下两档常驻；
Ollama 一旦换出模型，下次调用要重新从磁盘加载 7B，那几秒比省下的解码时间更长。

线上只有 7B 一档，跑在 GPU 上（`ollama ps` 显示 `100% GPU`，4.8 GB）。

## 引用校验：不让模型碰原文

引用最初的做法是让模型复制一段原文当 `quote`，再校验它是不是某条证据的连续子串。
实测 qwen2.5 会把证据**翻译成中文**再当引用提交——source 对、内容也对，但它不是引用。
换了三种 prompt 措辞做 A/B（7/12、6/12、1/12），没有改善，最强那版还让模型陷入重复输出，
把 Ollama 打挂了。

所以改成结构上堵死：模型只输出**证据编号**，原文由 `schema.resolve()` 从 evidence 里取出填进去。
模型没有机会转述，因为转述的通道不存在了。校验随之简化成一个范围判断。
这不是 prompt 工程问题，是数据流问题——让模型做它做不好的事（逐字复制），
不如让它只做一次选择。

`confidence` 字段实测会被写成 `85` 而不是 `0.85`，`schema.py` 里有一步百分制换算：
一次格式化偏差不该让整次诊断作废，但结构合法不等于数值合法，这一步要显式做。

## 已知缺陷

1. **关键词命中率是当前主要瓶颈。** 7B 的 5 条失败里有 3 条是没答到期望关键词，不是引用问题。语料从 4 篇扩到 7 篇后通过数从 7 涨到 10，说明瓶颈在检索覆盖而非模型。
2. **`manifest.py` 带问题重生成并不总能修好。** 实测部分用例两轮都缺同一项，问题原样重复。两轮上限是对的，但"重生成能修好"是一个被数据推翻的假设。
3. **incident 类用例依赖 `chaos/pods.yaml` 里的四个故障 Pod。** 集群里没有这些 Pod 时，`kubectl` 返回找不到资源，那几条失败反映的是环境缺失，不是模型能力。
4. **检索用的是朴素余弦，没有 rerank。** 个别用例的目标 chunk 排在十几位，top-4 取不到；再加大 k 只会引入无关证据并拖慢延迟。
